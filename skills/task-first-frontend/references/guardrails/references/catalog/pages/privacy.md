## Privacy
URL: https://developer.apple.com/design/human-interface-guidelines/privacy

Universal rules:
- MUST request access only to data the app actually needs. | topic: data minimization | source: Best practices | why: asking for more data than a feature needs makes it hard for people to trust the app | check: every requested data type is used by a feature that needs it.
- MUST NOT ask for data before a person shows interest in the feature that uses it. | topic: request timing | source: Best practices | why: premature requests make people distrust the app | check: each request appears when the related feature is first used or requested.
- MUST make permission requests as specific as possible so people have precise control over their data. | topic: precise permission scope | source: Best practices | why: precise control lets people decide with confidence | check: each request names one specific data type or resource.
- MUST be transparent about the privacy-related data and resources the app requires. | topic: disclose required data and resources | source: Privacy (introduction) | why: people are less comfortable sharing data when they do not know what is needed | check: the app states which privacy-related data and resources it requires.
- MUST be transparent about how the app collects and uses people's data. | topic: disclose collection and use | source: Best practices | why: people are less likely to share data they do not understand | check: the app explains the purpose of each data collection.
- MUST disclose privacy practices and privacy-relevant data collection to people before they download or commit to the app. | topic: pre-download privacy disclosure | source: Privacy (introduction) | why: people use these details to make an informed decision before they download | check: privacy details are visible before download or first use.
- MUST respect people's choices to use system-level privacy protections, such as relay addresses that hide a person's real email address. | topic: respect privacy protection choices | source: Best practices | why: people may deliberately limit what the app can see | check: the app works correctly and honors data handling when a privacy protection is enabled.
- MUST understand and meet every obligation that applies to tracking people across apps and services. | topic: tracking obligations | source: Best practices | why: tracking is a sensitive issue | check: tracking obligations are identified and implemented before tracking starts.
- MUST process data on the device where possible instead of sending it to a remote server. | topic: on-device processing | source: Best practices | why: avoids lengthy and potentially risky round trips to a remote server | check: each data-processing step is evaluated for on-device feasibility.
- MUST use platform-provided encryption and key management for stored data where the platform offers them. | topic: platform encryption and keys | source: Best practices | why: system-provided protections are maintained by the platform and reduce risk | check: sensitive stored data uses platform encryption and key management where available.
- MUST use platform-provided security technologies to store information locally, authorize people for specific operations, and transport information across a network. | topic: platform security technologies | source: Protecting data | why: people's information must stay protected in storage, authorization, and transit | check: local storage, authorization, and network transport each use a platform-provided security technology.
- MUST request permission before accessing personal data, including location, health, financial, contact, and other personally identifying information. | topic: personal data permission | source: Requesting permission | why: personal data requires the person's permission | check: each access to personal data is gated by a permission request.
- MUST request permission before accessing user-generated content, such as emails, messages, calendar data, contacts, gameplay information, media activity, smart-home data, and audio, video, and photo content. | topic: user-generated content permission | source: Requesting permission | why: user-generated content requires the person's permission | check: each access to user-generated content is gated by a permission request.
- MUST request permission before accessing protected resources, such as nearby wireless peripherals, home automation features, network connections, and local networks. | topic: protected resource permission | source: Requesting permission | why: protected resources require the person's permission | check: each access to a protected resource is gated by a permission request.
- MUST request permission before using device capabilities such as the camera and microphone. | topic: device capability permission | source: Requesting permission | why: device capabilities require the person's permission | check: each use of the camera or microphone is gated by a permission request.
- MUST request permission only when the app clearly needs the data or resource. | topic: clear need for permission | source: Requesting permission | why: people are suspicious of requests for personal information or device access without an obvious need | check: each request has an obvious, stated need in the current context.
- MUST NOT request permission at launch unless the data or resource is required for the app to function. | topic: no launch-time requests | source: Requesting permission | why: launch-time requests are only welcome when their purpose is obvious | check: every launch-time request is required for core function.
- MUST write permission explanations that clearly describe how the app uses the requested ability, data, or resource, and why. | topic: explain use and purpose | source: Requesting permission | why: the explanation is what people read when deciding | check: each explanation states how and why the app uses the requested item.
- MUST write each permission explanation as one brief, complete, active sentence that is specific and easy to understand, in sentence case, ending with a period. | topic: explanation form | source: Requesting permission | why: the example "The app records during the night to detect snoring sounds." is active and specific | check: each explanation is one complete active sentence with sentence case and a final period.
- MUST NOT write permission explanations that are vague, passive, or bare commands without a justification. | topic: explanation quality | source: Requesting permission | why: "Microphone access is needed for a better experience." is vague and "Turn on microphone access." gives no reason | check: each explanation gives a concrete reason and is not a bare command or a vague passive phrase.
- MUST include only one button on a custom screen shown before a permission request, and that button must clearly open the request. | topic: single-action pre-permission screen | source: Pre-alert screens | why: extra buttons can divert people from making their own choice | check: the pre-permission screen has exactly one button and it opens the request.
- MUST NOT include additional actions on a custom screen shown before a permission request, unless needed to obtain legal consent. | topic: no extra actions before request | source: Pre-alert screens | why: options such as close or cancel can keep people from ever seeing the request | check: the only action on the screen opens the request, unless legal consent requires more.
- MUST NOT title a custom pre-permission button with "Allow" or a similar term; MUST use a term such as "Continue" or "Next" that says the button opens the request. | topic: button wording | source: Pre-alert screens | why: a custom button that looks like the allow choice can lead people to accept without meaning to | check: the custom button label clarifies that it opens the request.
- MUST NOT show a custom screen before a tracking or permission request that could confuse or mislead people. | topic: no misleading pre-screen | source: Tracking requests | why: people sometimes tap quickly to dismiss alerts without reading them | check: the screen is clear about what happens next and does not mislead.
- MUST NOT offer incentives to influence a tracking request. | topic: no tracking incentives | source: Tracking requests | why: incentives are a prohibited manipulation in tracking requests | check: no reward, benefit, or inducement is attached to accepting tracking.
- MUST NOT design a custom screen that imitates a permission request. | topic: no imitation requests | source: Tracking requests | why: a screen that looks like a request confuses people about who is asking | check: custom screens are visibly distinct from system permission requests.
- MUST NOT show an image of a permission alert in a custom screen. | topic: no alert images | source: Tracking requests | why: an image of an alert is a prohibited design that mimics the real request | check: no custom screen contains a picture of a permission alert.
- MUST NOT annotate the screen behind a system permission alert. | topic: no alert annotations | source: Tracking requests | why: annotations on the screen behind the alert steer the person's choice | check: nothing is drawn over or next to the content behind an alert.
- MUST NOT design custom screens that take advantage of people's quick dismissal of alerts to influence their choices. | topic: no exploiting quick dismissal | source: Tracking requests | why: such designs use hasty taps to produce choices people did not intend | check: custom messaging before a request does not rely on hasty dismissal to succeed.
- MUST let people review and change their permission choices later. | topic: revisit permission choices | source: Requesting permission | why: people need to be able to change a choice after they have made it | check: there is a way for people to see and change each permission choice.
- MUST keep custom permission controls legible, with no low-contrast color combinations and no excessive translucency. | topic: legible custom controls | source: Location button | why: a control people must trust has to be readable | check: custom control colors meet contrast needs and translucency stays limited.
- MUST make text in custom permission controls fit without truncation at all accessibility text sizes and in every translated language. | topic: control text fit | source: Location button | why: truncated text makes a control's purpose unclear | check: the label fits at the largest accessibility size and in each supported language.
- MUST use passwordless authentication where possible instead of relying solely on passwords. | topic: passwordless authentication | source: Protecting data | why: passwords alone are weaker protection | check: each authentication flow offers passwordless sign-in where the platform supports it.
- MUST require two-factor authentication whenever passwords must still be used for authentication. | topic: two-factor authentication | source: Protecting data | why: passwords alone are not enough when they must be kept | check: every password-based sign-in requires a second factor.
- MUST use biometric identification to protect access to apps that people keep logged in, where the device supports it. | topic: biometric protection | source: Protecting data | why: logged-in apps need a further layer of protection on the device | check: access to a kept-logged-in app is gated by biometrics where available.
- MUST store sensitive information in the platform's secure credential store. | topic: secure credential store | source: Protecting data | why: a secure store gives a predictable and safer experience for private information | check: sensitive information is never kept in ordinary storage.
- MUST NOT store passwords or other secure content in plain-text files, even when file permissions restrict access. | topic: no plain-text secrets | source: Protecting data | why: encrypted secure storage is much safer than file permissions | check: no plain-text file holds passwords or secure content.
- MUST NOT invent custom authentication schemes when the app requires authentication. | topic: no custom authentication | source: Protecting data | why: custom schemes are less tested and less predictable | check: authentication uses established schemes only.
- MUST prefer established, system-provided sign-in features, such as password autofill, over custom sign-in. | topic: prefer system sign-in | source: Protecting data | why: system-provided features are maintained and familiar to people | check: sign-in uses system-provided features where the platform offers them.
- MUST NOT assume that only one person uses the app or is signed in on the device, because several people may be active on the same system. | topic: multiple users | source: macOS | why: fast user switching lets several people be active on one system | check: no logic assumes a single signed-in person per device.

Persona and journey notes:
- Show the current context first so people understand why access is requested, and place the request where the feature is used.
- For a navigation app, people already understand the need for location, so the request fits the first use of navigation.
- For a game that needs information about the surroundings, ask for permission before the game starts, so the request is expected.
- For a feature people use only occasionally, consider a single-action, one-time permission option so they can benefit without repeated prompts.
- A consent screen shown before or after a permission request is allowed when local privacy law requires it.
- Customize custom controls to match the app's UI, within the legibility limits above.
- Keep any custom screen before a request to a single clear action that opens the request.
- Where people may share a device, design sign-in and data views so one person's data is not shown to another.
