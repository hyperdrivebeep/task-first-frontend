# 클라이언트 실행 결함 리뷰

이 문서는 프론트엔드 소스의 실행 결함과 클라이언트·서버 경계의 실패를 코드 리뷰로 찾을 때 쓴다. 비동기 경쟁, 컴포넌트 수명, 폼 이벤트, 브라우저 저장소, SSR·내비게이션, 값 변환, API 연결이 대상이다. 이 문서가 맡는 것은 메커니즘, 즉 잘못된 클라이언트 결과를 만들 수 있는 코드 경로를 찾는 일이다. 상태별 문구와 다음 행동, 화면 사용성, 브라우저 E2E 관찰은 묶음의 다른 문서가 맡는다. 원래 review-frontend 스킬은 메커니즘과 상태 설계·화면 검사를 섞어 다뤘고, 이 문서는 그중 메커니즘만 이어받는다.

## 1. 필요성 판단: 무엇을 이해하거나 검증해야 하는가?

### 범위와 증거 확정: 어느 리비전의 어떤 경로를 따라가는가?

소스 리비전을 고정하고 실제 사용자 행동을 이벤트 핸들러, 로컬 상태, 요청, 응답, 렌더링 결과까지 따라간다. 주장하기 전에 상위 가드와 실제 프레임워크·런타임 설정을 읽는다. 접근할 수 없었던 경로와 실행하지 않은 경로는 그렇다고 적는다.

런타임에 따라 달라지는 발견이나 수정안을 권하기 전에는 해당 프레임워크·플랫폼 버전의 1차 자료를 확인하고, 결함이 실제로 성립하는지와 수정안을 바로 적용할 수 있는지를 따로 판단한다.

런타임 결함이 의심되면 브라우저 검증이 필요할 수 있고, UX 검토 중에 이런 결함이 드러날 수도 있다. 이때는 증거를 공유하고 원인 하나에 발견 사항 하나를 둔다.

## 2. 방법 결정: 어떤 증거를 어떤 방법으로 얻을 것인가?

### 규칙 적용: 어떤 메커니즘이 결과를 틀리게 만드는가?

#### UI-01: 요청 상태 대응

요청 시작, 완료, 거절, 취소가 일으키는 상태 갱신을 추적한다. 완료가 현재 작업의 것인지, 오류가 기계적으로 빈 성공으로 바뀌거나 성공이 이전 실패로 남지 않는지 확인한다. 재진입 클릭과 제출 가드를 실제 API 효과와 대조한다. 실패를 만드는 할당이나 분기를 짚어 내고, 문구와 다음 행동이 제품 상태에 맞는지는 [상태별 안내와 다음 행동](state-design.md)에 넘긴다.

#### UI-02: 비동기 경쟁과 낙관적 쓰기

도달할 수 있으면 입력 A, 입력 B, 응답 B, 응답 A 순서를 구성한다. 계정·테넌트·경로 변경을 포함해 식별 가드, abort 처리, 캐시 키를 확인한다. 낙관적 롤백이 이후의 편집이나 확정된 작업을 덮어쓰는지 본다. 요청을 abort했다고 서버가 아무 효과도 내지 않았다는 증명은 되지 않는다. 특정 취소 API를 요구하지 말고 기존 가드를 읽는다.

#### UI-03: 컴포넌트 수명과 파생 상태

effect 의존성과 정리, 타이머·구독·리스너, 오래된 클로저, 불안정한 key, 소유자가 바뀌어도 남는 상태를 살핀다. 서버 데이터, 로컬 초안, 파생값 사이의 동기화를 추적한다. 실제로 틀린 결과나 자원 수명 문제를 설명해야 하며, 반복 렌더링 자체를 결함으로 부르지 않는다. 개발 모드에서만 일어나는 프레임워크 동작과 운영 동작을 구분한다.

#### UI-04: 폼 이벤트와 입력 직렬화

지원되는 범위에서 기본 submit, Enter, 클릭, 조합 입력(composition), 붙여넣기, 자동완성 경로를 추적한다. 이벤트 중복 발생, 입력 유실, controlled·uncontrolled 전환, 빈 값·null·생략된 값, 서버 오류가 필드 상태를 갱신하는 방식을 확인한다. disabled·read-only와 기본 폼 의미가 의도한 이벤트와 맞는지 본다. 사용자에게 보이는 필드 설명과 복구 선택지는 UX 쪽의 몫이고, 클라이언트 검증은 서버 권한 검사가 되지 못한다.

#### UI-05: DOM 상호작용 메커니즘

의미 요소와 이벤트 처리가 키보드 실행, 포커스 이동·복원, 다이얼로그 수명, 동적 상태 안내를 깨뜨릴 수 있는지 본다. 조건부 렌더링과 언마운트를 거치는 ref와 포커스 대상을 추적한다. 정적 소스로 일부 결함은 확정할 수 있지만, 실제 스크린리더 동작이나 보이는 포커스, 접근성 준수는 증명하지 못한다. 화면·상호작용 검증은 [브라우저 증거와 판정](browser-evidence.md)과 [사용성 리뷰](usability-review.md)와 나누고, 그 체크리스트 전체를 되풀이하지 않는다.

#### UI-06: 브라우저 저장소, SSR, 내비게이션

브라우저 API의 사용 가능 여부와 예외, 저장소 거부·용량 초과, 서버와 클라이언트의 초기값 차이와 hydration을 확인한다. 새로고침, 딥링크, 뒤로·앞으로 가기, 다른 탭의 세션 변경, 재연결을 실제 상태 소유자까지 추적한다. 프레임워크·플랫폼 버전의 동작은 1차 자료로 확인한다. 지원하지 않는 환경을 지어내 계약 요구로 삼지 않는다.

#### UI-07: 클라이언트 경계의 값 변환

날짜·시간대, 로케일, 숫자 단위, 식별자가 표시값, 초안 상태, 저장소, API payload 사이에서 어떻게 바뀌는지 추적한다. 화면에 보이는 문자열이 왕복 변환된다고 가정하지 말고 파서와 직렬화기를 확인한다. 계약이 요구하면 값 없음을 0이나 빈 입력과 구별해 보존한다. 번역 품질과 화면의 줄바꿈은 이 규칙의 범위 밖이다.

#### UI-08: API 연결과 실패 전파

핸들러가 현재 자원 식별자와 자격 증명으로 의도한 실제 엔드포인트를 호출하는지, 실제 응답·오류 계약을 대응시키는지, 올바른 캐시를 무효화하거나 갱신하는지 확인한다. 응답 본문 파싱, 다운로드와 object URL의 수명, 목 응답이 운영에서도 도달 가능한지 본다. 보안 권한과 백엔드 보장은 서버 담당 검토와 협의하고, UI 컨트롤이 그것을 강제한다고 가정하지 않는다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 증거와 반증: 이 주장을 무너뜨릴 수 있는 코드는 없는가?

실제 식별자·위치와 런타임 소유자, 트리거, 순서대로 일어나는 이벤트·요청·응답·상태 변화, 깨진 계약, 사용자에게 보이는 결과를 적는다. 요청 가드, 로더, 오류 경계, 브라우저 래퍼, 컴포넌트 기본 요소처럼 주장을 반박할 수 있는 곳을 확인한다.

소스로 추적한 것(SOURCE_TRACED)과 실행한 것(EXECUTED)을 구분한다. 브라우저 증거에는 실제 역할, 상태, 브라우저 조건을 적고, 소스 검토를 화면 관찰처럼 쓰지 않는다. 재현 가능한 회귀 테스트는 빠진 가드나 잘못된 전이 때문에 실패해야 하며, 무관한 시간 초과로 실패한 것은 재현으로 치지 않는다. 순서대로만 응답하는 목으로는 비동기 경쟁을 증명할 수 없다.

### 결과 작성: 검증자가 판정할 수 있는 형태인가?

발견 사항은 확정하지 않은 후보로 적고, 판정에 필요한 맥락이 부족하면 그 사실을 함께 적어 검증할 사람이 판단하게 한다. 각 발견에는 반증, 수정안의 조건, 제안 테스트를 붙인다. 발견이 없어도 살펴본 경로, 확인한 안전장치, 남은 범위를 기록한다. UX나 화면 고유의 발견은 UI-01부터 UI-08까지의 규칙 ID에 끼워 넣지 않는다.
