# UI 검증 묶음

이 문서는 묶음의 유일한 진입점이다. 요청이 답해야 할 질문을 먼저 정해 필요한 참고 문서만 읽는다. 각 단계에 둔 공통 규칙은 모든 참고 문서에 그대로 적용한다. 참고 문서는 이 공통 규칙을 반복하지 않으므로, 참고 문서만 읽고 판정하지 않는다.

## 1. 필요성 판단: 이 작업은 어떤 질문에 답해야 하는가?

요청과 변경 범위를 보고 아래 질문 중 실제로 답해야 하는 것만 고른다. UI 코드가 있다는 이유만으로 모든 문서를 읽지 않는다. 한 작업이 여러 질문에 걸치면 해당 문서를 함께 읽되, 같은 문제는 원인이 있는 문서 하나에서 판정한다.

### 범위와 기대값

요청받은 흐름과 변경의 영향을 받는 상태를 먼저 검증한다. 작은 수정에 전체 서비스 검사나 모든 상태 조합의 실행을 강제하지 않고, 실제 코드 경로와 사용자 영향에 근거해 대표 조건과 경계 조건을 고른다.

기대값은 요구사항, 기존 결정, 합의된 제품 동작에서 가져온다. 현재 구현이나 방금 찍은 화면을 정답으로 삼지 않으며, 명시된 요구사항과 구현에서 관찰한 동작과 추정을 구분한다. 제품 규칙이 불명확하면 그 항목은 판정을 보류하고 독립적으로 확인할 수 있는 검사는 계속한다. 합격 기준을 바꾸는 중요한 결정만 확인을 요청하고, 나머지는 가정을 기록한 채 진행한다. 기능에 없는 보존·복구·중복 방지 요구를 임의로 만들어 결함으로 확정하지 않는다.

## 2. 방법 결정: 어떤 문서와 방법으로 증거를 얻을 것인가?

문서 사이의 경계는 다음과 같다. 상태별 문구와 다음 행동이 맞는지는 상태별 안내 문서가, 그 상태를 틀리게 만드는 코드 경로는 클라이언트 실행 결함 문서가 맡는다. 응답 역전과 비동기 경쟁은 코드 리뷰에서는 UI-02가, 테스트 설계에서는 행동 흐름 문서가 맡고, 전이 중 유지 조건 문서는 경쟁의 결과로 무엇이 화면에 남아야 하는지만 다룬다. 처리 중·실패·복구를 실제 화면과 요청·저장 기록으로 판정하는 일은 브라우저 증거 문서가 맡는다. 탐색형 QA는 넓은 여정 탐색과 보고 형식을 맡고, 개별 판단 기준은 해당 문서를 따른다.

### 실행한 것만 검증으로 쓴다

소스를 읽어 추적한 결과와 실제로 실행해 관찰한 결과를 구분해 적는다. 문서나 테스트 코드만 작성했다면 실행 검증을 마쳤다고 보고하지 않고, 도구가 지원하지 않는 모바일 화면·네트워크 제어·화면 비교를 실행했다고 추정하지 않는다. 생성하지 않은 파일, 촬영하지 않은 화면, 수행하지 않은 행동을 확보한 것처럼 쓰지 않으며, 줄 번호나 통과 기록을 지어내지 않는다.

모킹한 응답이나 의존성으로 통과한 검사는 그 의존성의 실제 동작까지 증명하지 않는다. 모킹으로 통과한 흐름은 실제 데이터 조건에서 한 번 더 확인하고, 확인하지 못했다면 그 부분을 미검증으로 남긴다. 검증을 시작할 때 지금 보는 화면이 테스트 데이터인지 실제 계정 데이터인지 확인해 보고에 적고, 두 경우의 결과를 섞어 판정하지 않는다.

테스트 도구를 썼다는 사실이나 오류가 없었다는 사실만으로 통과시키지 않는다. 테스트의 관찰 범위보다 강한 보장을 주장하지 않는다.

### 기다림과 기준을 조작하지 않는다

고정된 시간만큼 기다려 타이밍을 추측하지 않고, 검사할 상태가 되었다는 관찰 가능한 사건이나 상태를 기다린다. 테스트를 통과시키려고 대기 시간을 늘리거나 허용 오차를 넓히거나 locator·기대값을 바꾸지 않는다. 예상하지 못한 UI 변화에 맞춰 검사를 고치기 전에 같은 대상·동작·결과인지 먼저 확인한다. 테스트 편의를 위해 제품의 기대 동작이나 합격 기준을 바꾸지 않는다.

### 화면 크기와 테마의 기본 범위

반응형 웹이고 기기가 지정되지 않았다면 데스크톱 1440×900과 좁은 모바일 390×844 CSS px를 기본으로 확인하고, 제품이 다크 모드를 지원하면 라이트와 다크를 짝으로 확인한다. 이 값은 대표값이며 모든 기기를 대표하는 인증값이 아니다. 기본 범위 중 확인하지 않은 크기나 테마가 있으면 보고에 무엇을 왜 생략했는지 적고, 생략한 조건은 검증 완료 범위에 넣지 않는다. 모바일 크기 검사가 실제 기기의 키보드·터치 동작까지 증명하지는 않으며, 실제 실행한 조건만 결과에 포함한다.

### 안전 경계

이 묶음은 검증 지침이며 도구 설치·실행, 코드 수정, 외부 이슈 등록, 배포, 외부 메시지 전송의 권한을 주지 않는다. 리뷰 요청은 발견 사항과 수정 제안까지이고, 구현까지 요청받았을 때만 승인된 범위에서 수정한다.

게시·예약 발행·메일·SMS·결제·삭제·실사용자 권한 변경처럼 외부에 영향을 주는 조작은 테스트용으로 격리되었거나 명시적으로 허용된 범위에서만 실행한다. 허용되지 않은 마지막 단계는 직전까지 관찰하고 결과를 미검증으로 남긴다. 다른 사람의 데이터나 작업을 수정·삭제하지 않고, 권한 우회를 시도하지 않는다. 운영 시스템에 결함을 주입하지 않는다. 직접 만든 테스트 서버·탭·데이터·보류 요청은 필요한 증거를 보존한 뒤 정리하고, 다른 작업의 자원은 종료하지 않는다.

증거와 보고에서 비밀번호, 토큰, 쿠키, 인증 헤더, 개인정보를 제거하거나 가린다.

### 브라우저 도구

브라우저 조작은 작업 환경의 지침과 사용자가 지정한 도구를 따른다. aside-browser를 쓰라는 지침이 있으면 그 스킬의 현재 SKILL.md를 읽고 `aside guide`를 실행해 안내를 따르며, 스크린샷과 DOM을 직접 조사해야 하면 `aside guide repl`도 먼저 읽는다. 목록에 없으면 로컬 스킬 경로를 검색하고, 설치·업데이트·로그인 문제는 그 스킬의 절차로 처리한다. 명령이나 API를 이 묶음에 복제해 고정하지 않는다. 기존 테스트, 응답 제어 장치, 실행 기록이 있으면 먼저 재사용한다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 판정 4종

필수 확인 항목은 하나씩 통과·실패·미검증·해당 없음 중 하나로 남긴다.

통과는 조건을 재현하고 기대 동작을 실제 관찰값과 증거로 확인했다는 뜻이다. 실패는 기대 동작과 다른 결과를 확인했다는 뜻이며, 필수 항목 하나라도 실패하면 그 시나리오는 실패다.

미검증은 필요한 조건이나 관찰을 확보하지 못한 경우다. 권한·환경·안전 경계로 막힌 것인지, 시간 안에 실시하지 않은 것인지, 일부만 확인한 것인지 이유를 적는다. 실패가 없어도 필수 항목이 미검증이면 전체를 통과로 올리지 않는다.

해당 없음은 그 항목이 이 화면이나 흐름에 적용되지 않는 경우다. 적용되지 않는 근거를 적고, 확인하지 못한 항목을 해당 없음으로 분류하지 않는다.

재현할 수 없는 상태를 정상으로 간주하지 않는다. 자동 테스트 통과와 실제 브라우저 결과는 따로 기록한다.

### 증거는 마지막 수정 뒤의 것만 인정한다

판정에 쓰는 화면·캡처·기록은 대상 소스를 마지막으로 수정한 뒤에 만든 것이어야 하고, 그보다 오래된 증거는 다시 만든다. 재시도에서 성공해도 첫 실패는 지워지지 않으며, 새로고침·재로그인·대체 경로로 복구했다면 각각의 결과를 남긴다. 재시도에서만 수집한 기록을 최초 실패의 증거로 제시하지 않는다. 실패하면 초기 조건, 사건 순서, 기대값, 실제 결과와 행동 전후 화면·요청 기록을 보존한다. 결과는 기존 기록 형식을 쓰되 필수 근거가 빠진 것을 알아볼 수 있게 남기고, 대화의 기억만으로 결과를 재구성하지 않는다.

### 관찰과 해석을 나눈다

실제로 본 사실, 사용자 영향에 대한 추정, 기술적 원인 가설을 구분해 쓴다. 실제 사용자 조사를 하지 않았다면 그 검토를 휴리스틱 리뷰로 부르고, 사용자 발언·성공률·전환율 같은 반응을 관측한 것처럼 쓰지 않는다. 계측하지 않은 수치나 이동량을 만들지 않는다. "느리다", "헷갈린다", "직관적이지 않다"로 끝내지 말고 어떤 행동 뒤에 무엇이 보였고 사용자가 무엇을 알 수 없는지 설명한다.

### 한 원인은 한 번만 센다

같은 원인으로 여러 화면이나 여러 문서의 관점에서 드러난 문제는 발견 사항 하나로 묶고 발생 위치와 대표 증거를 모은다. 원인이나 사용자 영향이 다른 문제는 억지로 합치지 않는다. 문제 개수 목표를 두지 않고, 개인 취향을 결함으로 올리지 않는다.

### 심각도

심각도는 현재 과업에 대한 영향으로 정하고 수정 난이도와 따로 적는다. 영향이 불확실하면 조건부로 적는다.

중대 피해는 데이터 손실이나 잘못된 실제 처리가 일어났거나 임박한 경우이며, 발견하면 관련 위험 행동을 멈추고 먼저 보고한다. 차단은 핵심 과업을 완료할 수 없거나 되돌리기 어려운 잘못된 결과·심각한 오조작을 유발하며 실질적인 우회 경로가 거의 없는 경우다. 큰 마찰은 완료는 가능하지만 잘못된 선택, 재입력, 반복 행동, 재확인, 우회, 지연이 의미 있게 생기는 경우다. 작은 마찰은 국소적인 해석·탐색 부담이나 가독성·일관성·미세 인터랙션 문제로, 과업은 계속할 수 있는 경우다.

### 보고: 무엇을 확인했고 무엇이 남았는가?

보고에는 검증 대상과 환경·버전, 데이터 종류(테스트 데이터 또는 실제 계정 데이터), 확인한 화면 크기·테마, 실행한 시나리오와 항목별 판정, 증거 위치, 모킹·관찰 범위, 미검증 항목과 이유, 남은 결정을 구분해 적는다. 구현·테스트·배포를 구분한다. 검증한 범위 안에서만 완료를 선언하고, 문제가 없으면 관찰한 범위에서 근거 있는 문제를 찾지 못했다고 쓴다. 확인하지 않은 기기·상태까지 통과했다고 말하지 않는다.

단순한 수정에 별도 분석 문서를 강제하지 않는다. 사용자에게 설명할 때는 익숙한 말로 원인과 필요한 조치를 풀어 쓰고, 전문 용어는 필요한 경우에만 뜻을 덧붙인다.

근거 문헌의 적용 범위를 설명하거나 기준이 충돌할 때만 [근거 문헌과 적용 범위](references/sources.md)를 읽는다.
