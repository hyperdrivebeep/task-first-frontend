# 시작과 범위, 도구, 인계

이전 SKILL.md 본문에서 옮겨 온 규칙이다. 단계 라우터([../SKILL.md](../SKILL.md))와 같이 적용한다.

## 시작과 범위

- 첫 응답에서 적용 사실과 산출물을 짧게 말한다. 능력 확인으로 끝내지 않는다.
- 요청이 조사/설계, 선택된 시안 구현, 기존 설계의 작은 수정, 결과 검증 중 어디까지인지 읽고 계약의 `scope`(`design-only` / `implement` / `small-fix`)로 적는다. 이는 내부 구분이며 사용자가 고를 별도 승인 절차가 아니다.
- 제품·흐름·얻을 결과가 명확하면 가정을 설명하고 진행한다. 문서·코드에서 답할 수 없는 핵심 누락만 질문한다.
- 첨부 이미지가 제품 화면인지, 문서 링크가 있는 대화 캡처인지 먼저 구분한다. 문서를 읽어 달라는 요청을 화면 복제로 바꾸지 않는다.
- 저장소 지침과 현재 작업서를 우선한다. 설계는 제품 수정·서버 재시작·모델 실행·공개를 자동 허가하지 않는다. 기존 승인과 선택은 재확인하지 않는다.
- 이미 선택한 시안이 있으면 선택을 보존한다. 작은 수정에 전체 조사와 세 시안을 강제하지 않는다(`scope: small-fix`면 S3·S4가 N/A). 그래도 S0·S1·S2·S5·S6·S7은 수정 범위만큼 통과해야 한다.

## 도구와 다른 스킬

- 코드 검색은 범위를 좁힌 `rg`와 실제 파일 읽기부터 한다. 다른 프로젝트 문서를 참고해도 그 프로젝트의 구현 지시를 현재 제품에 적용하지 않는다.
- Product Design을 적용한다면 `index`로 라우팅하고 `get-context`, `audit`, `ideate`, `image-to-code`, `design-qa` 중 해당 단계의 지침을 읽는다. 이미 제공된 맥락을 다시 묻지 않는다.
- ImageGen 시안은 built-in 이미지 도구를 사용한다. 파일 경로가 있는 참조 이미지는 먼저 보고 실제로 첨부한다. 글로만 묘사하고 첨부했다고 말하지 않는다. 이미지로만 만든 시안은 계약에 `alt_source: imagegen`을 적는다. 이때 게이트는 html/css 검사를 건너뛰고 WARN을 내므로, AS-1~AS-5 자가 점검을 이미지에서 직접 한다.
- 브라우저는 현재 호스트와 사용자 선택에 맞는 지원 도구를 쓴다. Codex Desktop의 Product Design 기본은 in-app browser다. 현행 도구 문서를 읽고 API를 추측하거나 별도 Playwright/CDP로 우회하지 않는다.
- Figma·Sites·배포는 사용자가 정한 산출물에 필요할 때 해당 스킬로 연결한다. 도구가 있다는 이유로 업로드·외부 게시를 추가하지 않는다.
- 도구가 없으면 가능한 코드/문서 분석은 계속하되 하지 않은 캡처·생성·실행을 했다고 쓰지 않는다. 그 단계의 게이트는 FAIL로 남고, 그대로 보고한다. 요청된 산출물 형식을 바꿔야 할 때만 차이를 설명하고 의사를 묻는다.
- 가드레일 패키지([guardrails/SKILL.source.md](guardrails/SKILL.source.md))가 이름을 드는 `design-taste`, `frontend`, `generative-ui`, `visual-qa` 스킬이 이 환경에 없으면 이 스킬의 해당 단계 문서가 그 역할을 맡는다. 레퍼런스와 아트 디렉션은 S3·S4, 캡처 절차는 S2·S6과 [verification/references/browser-evidence.md](verification/references/browser-evidence.md)가 맡는다.

## 보존할 구분

`코드 근거 ≠ 현재 서버 지문`, `공식 설명 ≠ 직접 사용`, `에이전트 UI 시험 ≠ 사람 사용성 실험`, `생성 시안 ≠ 구현`, `로컬 검증 ≠ 배포 완료`, `게이트 PASS ≠ 사용성 증명`을 구분한다.

보기 좋은 화면을 위해 미확인·미측정·부분 결과·실패·stale을 숨기거나 성공으로 바꾸지 않는다. 단계 위치를 완료율로, 제안을 승인으로, 접수를 처리 완료로 표현하지 않는다. 새 요청이나 화면 언어 변경이 기존 기록의 의미를 조용히 바꾸게 하지 않는다.

## 완료와 인계

- **설계만 요청:** 과업/완료 조건, 코드 근거, 현재 화면 관찰, 레퍼런스 적용표, 상태 계약, 비교 시안과 출처 보드, 개선 가설/검증 과업과 한계를 전달한다. 선택 전 구현을 완료했다고 말하지 않는다.
- **구현까지 요청:** 선택 시안과 차이, 정상 사용 흐름, 실제 검증 결과, 남은 범위, 실행 가능한 미리보기와 파일, 비포·애프터 쌍을 전달한다. 변경 ID로 [관찰한 자료·적용 근거](audit-and-research.md#설계로-연결)와 [구현 위치·전후 증거·검증 항목별 주장/근거](implementation-and-validation.md#마감)을 연결해 보고한다. 적용 확인과 개선 효과를 구분한다.
- **검증/보고만 요청:** 관련 변경과 제공/직접확인 증거 범위만 보고하고 전체 설계 양식이나 추가 구현을 강제하지 않는다.
- 산출물은 작업 폴더에 보존하고, 사용자가 다른 컴퓨터에서 볼 수 있게 저장소 브랜치·PR로 올려 링크를 준다. 임시 출력과 검토용 최종 산출물을 구분하고 기존 문서·dirty·다른 작업을 덮어쓰지 않는다.
- 중요한 결과를 먼저 말한다. 전체 근거는 문서에 두되 최종 답변이 앞선 진행 메시지 없이도 이해되게 한다. 마지막으로 통과한 게이트 단계와 `RESULT:` 줄을 적는다.
