# 브라우저 증거와 판정

이 문서는 브라우저 E2E 테스트를 설계·실행·보강할 때 처리 중·실패·복구의 UI 상태 변화와 화면 드리프트를 실제 증거로 판정하는 방법을 정한다. 작업을 끝냈다는 사실과 과정의 UI가 올바르다는 사실을 구분하고, 요구사항의 기대 상태, 실제 화면, 요청·저장 결과를 연결해 판정한다. 단순 사이트 탐색이나 일반 코드 리뷰에는 적용하지 않는다.

테스트 설계 요청에서는 기준과 시나리오를 쓰고, 실행 요청에서는 실제 증거를 모으고, 보강 요청에서는 빠진 검사와 필요한 최소 재현 장치를 더한다.

## 1. 필요성 판단: 무엇을 이해하거나 검증해야 하는가?

### 정상 기준: 실행 전에 각 행동의 기대 상태를 정했는가?

대상 행동마다 아래를 간결하게 기록한다.

시작 조건으로는 사용자 권한, 준비 데이터, 화면, 기존 저장값을 적는다. 행동과 사건에는 클릭·입력, 응답 도착, 실패, 재접속이 들어간다. 처리 중에 보여야 할 안내, 잠겨야 할 행동, 유지할 입력·선택을 정하고, 완료 후에는 성공·실패·결과 미확정별 표시와 다음 행동을 정한다. 사라져야 할 이전 폼, 로딩, 오류, 완료 안내도 정해 둔다. 결과 근거로는 저장값, 요청 수·대상, 화면과 이를 연결할 기록을 정한다.

서로 관련된 값의 일관성도 검사한다. 선택 수량, 대상별 수량, 생성 버튼 문구가 같은 개념을 나타내면 서로 맞아야 하고, 선택 수량과 현재 처리 가능한 수량이 다른 개념이면 둘을 구분하는 문구를 검사한다. 특정 제품의 숫자나 표시 규칙을 다른 제품에 고정해 적용하지 않는다.

## 2. 방법 결정: 어떤 증거를 어떤 방법으로 얻을 것인가?

### 전환 관찰: 다음 행동 전에 현재 상태를 다시 읽었는가?

중요한 행동 뒤에는 현재 화면을 새로 읽는다. 이전 화면의 좌표나 요소 참조가 계속 유효하다고 가정하지 않는다. 여러 행동을 묶더라도 검증해야 할 상태 경계를 건너뛰지 않는다.

처리 중 상태가 중요한 흐름은 다음 순서로 확인한다.

1. 대상 요청의 응답을 보류하도록 준비한다.
2. 실제 UI에서 행동한다.
3. 요청이 도착하고 해당 상태에 들어갔는지 확인한다.
4. 처리 중 문구, 잠금, 입력 보존, 수량, 화면 배치를 검사한다.
5. 응답을 해제하고 다음 상태를 확인한다.

렌더링이 안정된 것과 저장·생성이 완료된 것을 구분한다. 응답 제어가 없다면 실제로 관찰한 범위만 판정하고 중간 상태는 미검증으로 남긴다.

실패·복구는 관련 위험에 맞춰 고른다. 저장 전 거절, 저장 성공 후 응답 유실, 오래된 응답의 늦은 도착, 일부 대상만 실패한 경우를 구분한다. 응답 유실을 재현할 때는 저장 성공 근거도 확인하고, 성공 후 재조회·재접속이 중요한 흐름에서는 저장된 결과가 유지되는지 확인한다. 끝나면 보류 요청을 해제한다.

### 세 종류의 근거: 문구, 화면, 저장 결과를 모두 확인했는가?

먼저 문구와 상태를 본다. 제목, 수량, 선택값, 버튼 활성 여부, 입력 보존, 포커스, 이전 안내의 제거를 명시적으로 검사한다.

다음으로 실제 화면을 본다. 현재 viewport에서 가림, 잘림, 화면 밖 배치, 팝오버, 오류 뒤 다음 버튼을 확인한다. 페이지 전체 이미지나 DOM에 요소가 있다는 사실만으로 사용자가 볼 수 있다고 판정하지 않는다.

마지막으로 동작과 저장 결과를 본다. 실제 다음 행동을 수행하고 요청 대상·횟수·저장값을 확인한다. 성공 안내만으로 저장 성공을 단정하지 않는다.

일반 클릭과 키보드 조작을 우선한다. 강제 클릭, 스크립트로 직접 일으킨 이벤트, API 대체로 사용자 경로를 통과 처리하지 않는다. 진단용 우회가 필요하면 원래 경로의 결과와 분리해 기록한다.

자동 반복 검사는 명시적 assertion(기대값을 확인하는 검사), 접근성 구조 비교, 화면 이미지 비교를 필요한 범위에서 조합한다. 한 종류의 통과가 다른 종류의 검사를 대신하지 않는다. 도구의 visible 판정은 실제로 보인다는 뜻과 다를 수 있다. 예를 들어 Playwright의 visible은 크기가 있고 `visibility:hidden`이 아니라는 조건이어서, 다른 요소에 가려지거나 viewport 밖에 있거나 투명한 요소도 통과할 수 있다. 사용자가 봐야 하는 요소는 viewport 안의 위치와 가림 여부를 따로 확인하거나 해당 영역을 캡처해 본다.

### 화면 비교: 무엇을 무엇과 비교하는가?

비교는 두 가지로 나눈다. 같은 실행 안에서 행동 전·처리 중·행동 후를 비교하면 필요한 상태 전환이 일어났는지 알 수 있다. 이전에 정상으로 검토한 화면과 현재 실행의 같은 상태를 비교하면 코드 변경으로 생긴 뜻밖의 표시·배치 변화를 알 수 있다.

#### 선택된 시안의 보존

선택된 시안을 구현하거나 후속 수정을 검증할 때는 시안과 제품이 일치하는지도 확인한다. 기존 명세나 이슈에서 정확한 변형·버전 또는 스냅샷과 사용자의 추가 메모를 가져오고, 모든 화면에 새 비교 문서를 만드는 대신 영향을 받는 합의만 기존 실행 기록에 연결한다.

비교할 때는 네 가지를 확인한다. 메뉴·입력·주요 행동·과업 단계처럼 유지하기로 한 합의가 API 연결이나 후속 수정으로 빠지거나 바뀌지 않았는지 본다. 실제 차이가 명시적인 제품 결정과 연결되는지 보고, 최신 화면이라는 이유만으로 기준을 대체하지 않는다. 선택된 시안과 제품 화면은 같은 역할·데이터·상태·viewport에서 비교한다. 실제 요청·저장·복구 결과는 따로 확인하고, 모의 동작이나 이미지 일치만으로 통과 처리하지 않는다.

각 항목에 합의의 출처, 기대한 UI, 관찰한 UI와 증거를 연결한다. 정적 시안에 없는 처리 중·실패 동작은 유효한 제품 요구사항에서 기준을 찾고 임의로 추정하지 않는다. 기준이 없거나 서로 충돌하면 해당 항목을 미검증으로 남기고 독립적인 검사는 계속한다. 기능 테스트 통과와 선택된 디자인의 보존 여부는 따로 판정한다.

#### 이미지 비교의 조건과 기준 이미지

이미지 비교에서는 브라우저, OS, 폰트, viewport, 화면 배율, 언어, 시간, 테스트 데이터를 가능한 범위에서 일정하게 유지하고, 달라진 조건은 기록한다. 움직이는 콘텐츠나 시계처럼 결과와 무관한 변동값은 검증 목적에 맞춰 제어한다.

스크린샷은 검사하려는 상태가 확인된 다음 찍는다. 요청 중 화면을 검증한다면 그 요청이 실제로 대기 중인지 먼저 확인한다. 스냅샷 비교가 화면을 안정시키는 과정에서 과도 상태를 건너뛸 수 있으므로 전이 중 상태 검사는 따로 수행하고, 애니메이션을 끈 스냅샷만으로 실제 동작 중의 위치 안정성을 입증했다고 판단하지 않는다.

화면 전체의 차이가 중요하면 페이지를 비교하고, 수량·CTA·팝오버·툴바·상세 패널처럼 특정 영역만 중요하면 그 영역을 비교한다. 핵심 문구나 버튼을 가리거나 허용 오차를 넓혀 결함을 숨기지 않으며, 변동 영역을 제외할 때는 이유를 남긴다.

기준 이미지가 없으면 먼저 기준 후보를 만들고, 그것만으로 회귀 검사가 통과했다고 보고하지 않는다. 뜻밖의 차이를 없애려고 기준 이미지를 자동이나 일괄로 갱신하지 않는다. 갱신은 의도한 디자인 변경인지와 diff를 검토한 뒤 프로젝트의 기존 승인 절차에 맞춰 하고, 기준 이미지에는 검토 가능한 변경 이력을 남긴다. 이 문서 때문에 매번 별도 사용자 승인을 더하지는 않는다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 기록 연결: 판정마다 증거가 붙어 있는가?

시나리오, 상태, viewport, 소스 버전마다 기대값, 관찰값, 이미지, 요청 기록을 연결한다. 최초 실패를 조사할 수 있도록 행동 전후 화면과 요청 기록을 보존한다. 최종 보고에는 확인한 범위, 발견한 문제, 미검증 범위와 이유를 구분한다.

검사 체계를 새로 만들었다면 [행동 흐름 테스트 설계](behavior-flow-tests.md) 3단계의 "회귀 테스트와 탐지력"에 따라 결함을 일부러 넣어 검사가 실패하는지 확인한다.
