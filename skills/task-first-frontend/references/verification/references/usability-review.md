# 사용성 리뷰

이 문서는 Steve Krug의 Don't Make Me Think 원칙으로 실제 UI, URL, 스크린샷, 디자인 시안을 보고 사용자가 화면을 이해하고 다음 행동을 고르는 데 드는 불필요한 생각을 찾을 때 쓴다. 사용자는 페이지를 정독하거나 모든 선택지를 비교하기보다 훑어보고, 첫 번째로 그럴듯한 선택을 누르며, 작동 원리를 다 이해하지 않은 채 진행하는 경우가 많다. 책 요약만 요청받았거나 픽셀 차이 비교, 기능 테스트, 접근성 인증만 요청받은 경우에는 쓰지 않는다.

각 지적은 화면의 단서, 사용자가 풀어야 하는 의문, 과업 영향, 구체적인 수정, 확인 조건으로 이어서 쓴다. 아래 절차는 이 묶음의 운영 기준이며 저자가 만든 공식 평가표가 아니다.

## 1. 필요성 판단: 무엇을 이해하거나 검증해야 하는가?

### 범위와 입력: 어떤 사용자의 어떤 과업을 보는가?

사용자 목표, 대상 화면, 사용자 유형, 기기를 대화에서 파악한다. 빠진 정보가 진행을 막지 않으면 가정을 한 줄 적고 진행하고, URL이나 화면 자료가 전혀 없으면 대상만 요청한다.

기본 단위는 사용자의 과업이다. "기존 예약의 날짜를 바꾸고 결과를 확인한다"처럼 정하고, 메뉴를 전부 열어 보는 일을 과업으로 삼지 않는다. 범위가 넓으면 대표 과업부터 보되 요청된 화면이나 흐름은 빠뜨리지 않는다.

기존 제품의 사용자, 용어, 브랜드, 디자인 시스템을 존중한다. 전문 업무 도구에 필요한 밀도나 비교 정보를 복잡해 보인다는 이유만으로 없애지 않는다.

| 입력 | 점검 범위 | 확인하지 못한 것으로 남길 것 |
| --- | --- | --- |
| 실제 URL 또는 실행 중인 앱 | 화면과 허용된 상호작용, 전후 상태 | 방문하지 않은 흐름·권한·기기 |
| 스크린샷 또는 정적 시안 | 보이는 문구, 배치, 계층, 시각적 상태 | 클릭 결과, 숨겨진 내용, 실제 포커스·저장 동작 |
| 코드만 있음 | 실행 가능한 화면 확보 또는 구현상 우려 제시 | 렌더링을 보기 전의 화면 통과 판정 |

## 2. 방법 결정: 어떤 증거를 어떤 방법으로 얻을 것인가?

### 화면과 흐름 관찰: 처음 보는 사람이 무엇을 먼저 누르는가?

1. 처음 보이는 화면부터 본다. 코드를 읽거나 숨겨진 DOM을 찾기 전에 서비스·페이지의 정체성, 현재 위치, 눈에 띄는 다음 행동을 기록한다. 개발자가 아는 기능을 사용자가 알아낼 수 있다고 가정하지 않는다. 내비게이션을 검토한다면 홈을 거치지 않고 들어온 깊은 페이지도 하나 확인한다.
2. 첫 번째로 그럴듯한 선택을 적은 뒤 조작한다. 훑어보는 사용자가 먼저 누를 법한 라벨과 시각 단서로 예상 결과를 적고 실제 결과와 비교한다. DOM에 있는 요소가 화면에서도 발견된다고 결론 내리지 않는다.
3. 과업과 복구를 따라간다. 진입, 선택·입력, 완료 확인, 관련 오류·복구 상태를 보고, 첫 선택이 빗나갔을 때의 비용과 되돌아갈 단서도 확인한다. 검색·필터나 폼이 있으면 과업에 필요한 빈 결과와 검증 오류를 포함한다.
4. 화면 조건을 남긴다. URL이나 화면명, 역할, 데이터 상태, 뷰포트, 필요한 재현 순서를 적는다.
5. 증거를 보관한다. 발견 사항마다 실제로 본 스크린샷을 연결하고 위치를 설명한다. 첫 화면과 관련 부분을 구분하고, 전체 페이지를 줄인 이미지 한 장으로 글자 크기나 시인성을 판단하지 않는다. 기존 자료밖에 없으면 첨부 이미지 번호와 영역을 적는다.

각 단계에서 다음 네 가지를 묻는다. 묶음의 다른 문서도 처음 쓰는 사람의 과업을 따라갈 때 이 질문을 쓴다.

1. 지금 무엇을 해야 하는지 알 수 있는가?
2. 그 행동을 실행할 곳을 발견할 수 있는가?
3. 이름과 설명으로 원하는 결과가 나올지 예상할 수 있는가?
4. 실행한 뒤 진전했는지, 실패했는지 알 수 있는가?

### 판단 기준: 화면의 어떤 단서가 생각을 요구하는가?

모든 기준을 억지로 문제로 만들지 않고, 화면 단서와 과업에 이어지는 항목만 보고한다.

| 관점 | 화면에서 확인할 것 | 수정 방향 |
| --- | --- | --- |
| 즉시 이해 | 보자마자 무엇이며 어떻게 쓰는지 알 수 있는가? 새롭거나 복잡하다면 짧은 문구·이름·배치만으로 설명되는가? | 가능하면 자명하게, 불가하면 최소한의 설명으로 빠르게 이해되게 한다. 재치 있는 이름보다 명확한 이름을 우선한다. |
| 훑어보기 | 중요도가 두드러짐에 반영되고, 관련 항목이 묶이며, 포함 관계가 시각적으로 중첩되는가? 무시해도 되는 영역과 볼 영역을 구분할 수 있는가? | 강조, 그룹, 제목, 간격을 실제 관계에 맞추고 과업에 기여하지 않는 장식·구분선·반복 강조를 줄인다. |
| 관례와 학습비용 | 익숙한 관례를 버려야 할 이유가 있는가? 새 방식이 설명 없이 이해되거나 학습비용보다 큰 가치를 주는가? | 기존 관례를 우선하고, 혁신이 필요하면 기존 단서의 가치를 지킨 채 실제 사용자에게 확인한다. |
| 조작 가능성 | 클릭할 수 있는 것과 정보가 보기만 해도 구별되는가? 아이콘·라벨·상태로 행동과 동작 범위를 예상할 수 있는가? | 명시적 라벨과 일관된 단서를 쓰고 hover나 시행착오에 발견을 미루지 않는다. |
| 선택과 정보 향기 | 첫 번째로 그럴듯한 선택이 사용자 목표와 맞는가? 내부 약어·제품명·분류를 해석해야 하는가? 선택 뒤에도 맞는 길이라는 확신이 유지되는가? | 사용자의 언어로 선택지를 구분하고 다음 화면의 제목·상태를 앞선 라벨과 잇는다. 잘못 고른 결과와 복구를 예측할 수 있게 만든다. |
| 문구의 부담 | 정보 없는 환영·자기칭찬 문구나 읽히지 않는 장황한 지침이 핵심을 가리는가? | 문구를 과감히 줄이고 지침을 자가설명형 UI로 바꾼다. 기사·보고서 같은 실질 콘텐츠와 비용·제약·복구 정보는 남긴다. |
| 위치와 길 찾기 | 사이트·제품, 페이지 이름, 주요 영역, 현재 위치, 검색·돌아갈 경로를 깊은 페이지에서도 알 수 있는가? 진입 라벨과 도착 페이지명이 일치하는가? | 지속 내비게이션과 현재 위치 신호를 일관되게 하고, 경로 표시는 보조 수단으로 쓴다. 하위 단계까지 실제 화면으로 검토한다. |
| 홈과 첫 시작 | 처음 온 사용자가 무엇을 제공하고 무엇을 할 수 있으며 어디서 시작하는지 아는가? 검색·탐색·가입·로그인 진입점이 진입점처럼 보이는가? | 정체성, 핵심 가치, 제공 범위, 시작점을 먼저 드러내고, 프로모션이 큰 그림을 덮지 않게 우선순위를 정한다. |
| 배려와 신뢰 | 가격·제약·장애·지원 경로를 숨기거나 서비스 사정에 맞춘 불필요한 수고를 요구하는가? 실패가 이전 노력을 잃게 하는가? | 조건을 결정 전에 공개하고 입력을 보존하며 실제 도움과 정직한 상태·복구 방법을 준다. |
| 개인정보와 교환가치 | 필수·선택 입력이 과업에 정말 필요한가? 정보를 주고 무엇을 얻는지 아는가? | 필수와 선택 항목을 모두 줄이고 수집 이유와 사용자 이익을 가까이 설명한다. |

#### 페이지 유형별 추가 점검

- 홈·랜딩: 정체성, 제공 가치, 주요 콘텐츠·기능, 대상 사용자, 차별점, 시작점을 첫인상에서 파악할 수 있는지 본다. 명제가 자명하지 않으면 명확한 설명 단서를 주고, 모호한 슬로건이나 미션 문구로 때우지 않는다. 홈에 항목을 하나 더할 때마다 전체 계층과 핵심 시작점이 치르는 비용을 함께 본다.
- 깊은 페이지·내비게이션: 책의 trunk test처럼 홈을 가리고 임의의 하위 페이지에서 사이트·제품 식별, 페이지 이름, 주요 섹션, 로컬 내비게이션, 현재 위치, 검색이나 귀환 경로를 찾을 수 있는지 확인한다. 모든 항목이 늘 필요하다는 뜻은 아니며, 현재 과업에 필요한 길 찾기 단서가 독립적으로 남는지를 본다.
- 폼·등록·지원: 필요한 정보만 요구하는지, 형식을 과하게 강제하지 않는지, 비용·제약·장애·연락 수단을 숨기지 않는지, 오류 뒤 입력과 복구 경로가 남는지 본다. 도움말과 FAQ가 실제 질문을 다루고 최신인지 확인한다.

모바일과 접근성은 과업을 막는지 함께 본다. 잘림, 겹침, 고정 요소의 가림, 좁은 조작 영역, 읽기 어려움, 색만으로 구별되는 상태를 살핀다. 실행 환경이 있으면 의미 있는 헤딩과 링크 문구의 앞부분, DOM 읽기 순서, 폼 라벨 연결, 대체 텍스트, 본문 건너뛰기, 텍스트 확대, 키보드만으로 수행·복구할 수 있는지도 확인한다. 스크린샷이나 자동 검사만으로 접근성 준수, 대비 비율, 실제 터치 영역을 단정하지 않으며, 정량 기준이나 인증을 요청받으면 해당 표준과 보조공학을 따로 검증한다.

#### 피해야 할 오판

- 클릭 수를 절대 기준으로 삼지 않는다. 선택의 불확실성, 진행 중 확신, 반복 작업 부담, 실제 지연을 본다. 여러 번의 명확한 선택이 한 번의 모호한 선택보다 나을 수 있다.
- 사용자가 모든 문구를 읽고 최적 선택을 하거나 기능 원리를 정확히 이해한다고 가정하지 않는다.
- 의도와 다른 경로로 성공한 사용자를 잘못 썼다고 판단하지 않는다. 그 경로가 비효율, 오류 위험, 기능 발견 누락, 통제감 저하를 만드는지 구분한다.
- 스크롤, 긴 페이지, 여러 버튼, 아이콘, 정보 밀도 자체는 결함이 아니다. 목표를 방해하는 구체적인 단서가 있어야 한다.
- 책의 역사적 예시나 특정 배치·단어 수를 모든 제품의 고정 규칙으로 만들지 않는다. 기존 디자인 시스템과 현재 플랫폼 관례를 우선한다.
- 애니메이션, 강한 비주얼, 브랜딩 자체를 결함으로 보지 않는다. 핵심 과업을 늦추거나 가리는지, 경험 자체가 제품 가치인 맥락인지 판단한다.
- 팀의 취향이나 평균 사용자를 근거로 패턴을 찬반하지 않는다. 논쟁을 특정 사용자·과업·문구·맥락의 질문으로 바꾸고, 필요하면 작은 실제 사용자 테스트로 푼다.
- "촌스럽다", "더 깔끔하게"로 끝내지 않는다. 예쁜 정도에만 관한 선호는 심각도를 붙인 결함으로 세지 않는다.
- 에이전트가 몇 초 안에 답했다는 사실을 사람의 이해 속도로 보고하지 않는다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 근거 상태와 우선순위: 이 지적은 얼마나 확인되었는가?

"두 버튼이 모두 '계속'이며 구분 설명이 없다"는 관찰이고, "사용자가 예약 확정과 임시 저장을 혼동할 수 있다"는 해석이다. 발견 사항마다 근거 상태를 붙인다.

화면 관찰은 특정 화면·조건에서 시각적 문제를 직접 확인한 상태다. 동작 재현은 조작과 결과까지 확인하고 재현 순서를 기록한 상태다. 검증 필요는 우려는 있지만 관련 상태나 사용자 행동을 확인하지 못한 상태이며, 이때는 검증 방법을 제안하고 확정 결함과 구별한다.

영향이 큰 문제부터 제시하고 수정 규모는 따로 설명한다. 근거 없는 총점이나 통과 기준을 만들지 않는다.

### 대안 선택과 구현 인계: 고른 시안을 어떻게 넘기는가?

대안 비교를 요청받았거나 구현 전에 풀어야 할 디자인 선택이 있을 때만 적용한다. 간단한 리뷰마다 시안 제작이나 별도 승인을 요구하지 않는다.

- 같은 과업·역할·데이터·상태에서 현재 화면과 제안을 비교한다. 대안 수를 채우기보다 배치·문구·행동의 차이가 사용자 부담을 어떻게 바꾸는지 설명한다.
- 상호작용이 선택에 중요하고 시안 제작이 요청 범위에 있으면 기존 컴포넌트와 실행 환경으로 확인할 수 있는 미리보기를 만든다. 링크나 실행 경로와 구현된 상태를 적고 정적 화면·모의 동작·실제 연결 범위를 구분한다. 시안 제작은 외부 공개나 운영 배포의 허가가 아니다.
- 사용자가 고른 변형과 버전 또는 스냅샷, 선택 근거가 된 발언, 먼저 적용할 추가 메모를 기존 명세나 이슈에 연결한다. 바꿀 항목과 유지할 메뉴·입력·다음 행동·과업 단계를 짧게 남긴다. 시안 선택만으로 정책 변경이나 기존 기능 삭제까지 합의되었다고 보지 않는다.
- 구현 뒤 선택된 기준과 실제 화면이 같은지 확인하는 일은 [브라우저 증거와 판정](browser-evidence.md) 2단계의 "화면 비교"를 따르고, 시안의 사용성 판단과 실제 저장·요청·복구 검증을 구분한다.

### 결과물과 재검증: 무엇을 어떤 형식으로 남기는가?

사용자의 언어로 답한다. 먼저 과업을 가장 방해하는 문제를 요약하고 관찰 범위와 중요한 가정을 짧게 적는다. 작은 리뷰에 큰 보고서 형식을 강요하지 않는다.

```markdown
#### F01 · [심각도] 구체적인 문제
- 위치·조건: 화면, 사용자 역할, 뷰포트, 관련 상태
- 근거 [화면 관찰/동작 재현/검증 필요]: 스크린샷 링크 또는 첨부 번호·영역, 필요한 재현 순서
- 관찰: 실제로 보였거나 재현된 사실
- 사용자 부담: 생길 수 있는 의문과 과업 영향, 관찰 사실과 구분
- 원칙: 관련 판단 기준
- 수정 제안: 바꿀 문구·배치·강조·상태를 구체적으로
- 확인 조건: 같은 과업과 조건에서 무엇이 달라져야 하는지
```

"저장 버튼을 개선" 대신 "임시 저장과 외부 게시의 버튼명을 각각 구분하고 게시 범위를 실행 전에 표시"처럼 제안한다. 실제 동작을 모르면 문구를 확정하지 말고 필요한 확인을 함께 적는다. 마지막에 우선 수정할 항목과 미검증 범위를 남긴다.

수정한 경우 같은 과업, 역할, 데이터 조건, 뷰포트에서 다시 보고 원래 증거와 비교해 발견 사항의 상태를 해결, 일부 해결, 미해결, 재검증 불가로 갱신한다. 화면 단서의 개선은 시각적으로 확인할 수 있지만 사람이 더 잘 이해하는지는 실제 사용자 테스트로 확인한다. 수정에 영향을 받는 인접 상태만 더 확인한다.

화면 관찰만으로 결정하기 어려운 문제가 남을 때만 [실제 사용자 테스트](usability-user-testing.md)를 읽는다.
