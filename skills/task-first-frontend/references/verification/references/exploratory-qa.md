# 탐색형 UX QA와 HAR 보고

이 문서는 URL과 QA 계정으로 실제 브라우저에서 처음 쓰는 사용자 관점으로 서비스의 화면과 핵심 여정을 폭넓게 탐색하고, HAR와 화면 증거를 연결한 재현 가능한 보고서를 쓸 때 쓴다. 단순 디자인 의견, 픽셀 비교, 코드 수정 요청에는 적용하지 않는다.

## 1. 필요성 판단: 무엇을 이해하거나 검증해야 하는가?

### 역할과 목표: 무엇을 찾으려고 탐색하는가?

검증자는 이 서비스를 처음 쓰는 일반 사용자이자 사용자 여정과 인터랙션을 검증하는 UX QA 담당자로서, 제공된 QA 계정으로 로그인해 그 계정이 접근할 수 있는 여정을 넓고 깊게 탐색한다. 기능이 동작하는지에 더해, 사용자가 화면을 보고 판단하고, 클릭하고, 기다리고, 실수하고, 이전 작업으로 돌아오는 과정에서 겪는 불편·혼란·불안·불필요한 수고를 찾는다. 기능 오류뿐 아니라 layout shift, 상태 표시 부족, 애매한 문구, 시각적 위계, 입력 부담, 작업 복구, 피드백 부족도 조사한다.

탐색 내내 처음 쓰는 사람이 이 화면만 보고 현재 상황을 이해하고, 다음 행동을 고르고, 자기 행동이 제대로 처리되었다고 확신할 수 있는지 묻는다.

조사만 수행하며 따로 요청받지 않으면 제품 코드를 고치거나 디자인을 구현하지 않는다.

접속 정보로 서비스 URL, QA 계정(또는 안전한 자격 증명 전달 경로), 테스트 환경과 허용 범위를 확인한다. 환경이나 권한이 불명확하면 먼저 확인할 수 있는 정보를 조사하고, 로그인 정보처럼 꼭 필요한 정보가 정말 없을 때만 질문한다.

### 준비와 여정 지도: 무엇을 기록하고 어떤 여정을 돌 것인가?

#### 기록 시작

가능하면 로그인 전에 HAR 기록을 시작해 로그인부터 탐색 종료까지 네트워크 기록이 이어지게 한다. 테스트 일시와 시간대, 대상 환경과 브라우저, 화면 크기와 배율, QA 계정의 역할과 확인 가능한 접근 범위, 기본 네트워크 조건과 따로 적용한 테스트 조건을 함께 기록한다.

일반 데스크톱 화면에서 먼저 탐색하고, 좁은 데스크톱 화면에서도 주요 여정을 확인하며, 모바일 사용이 지원되거나 중요한 서비스라면 모바일 크기도 확인한다. 실제 사용한 화면 크기를 보고서에 적는다.

#### 화면과 여정 목록

로그인 뒤 접근할 수 있는 메뉴, 탭, 목록, 상세 화면, 버튼, 더보기 메뉴, 모달, 드로어, 설정, 도움말을 탐색해 지도를 만든다. 화면 목록과 사용자 여정은 구분하며, 여정은 어떤 목적으로 시작해 어떤 결과를 얻는지로 정의한다. 예를 들면 로그인해 지금 할 일을 파악하기, 목록에서 원하는 항목을 찾아 상세 내용 확인하기, 항목을 만들거나 고치고 저장 결과 확인하기, 작업을 확정하거나 예약하고 현재 상태 확인하기, 진행 중인 작업을 떠났다가 돌아와 이어서 처리하기, 실패한 작업의 원인을 이해하고 재시도하기가 있다. 예시는 서비스에 실제로 있을 때만 적용하고, 없는 기능이나 접근할 수 없는 관리자 기능을 가정하지 않는다.

여정마다 J01, J02 같은 ID를 붙이고 사용자 목적, 진입점, 주요 행동과 분기, 성공으로 판단할 종료 상태, 사전 조건과 필요한 테스트 데이터, 공통 판정을 기록한다. 눈에 띄는 주요 버튼만 보고 끝내지 않고 보조 행동, 접힌 메뉴, 취소·뒤로 가기·재진입 경로도 포함한다.

### 점검 범위: 어떤 종류의 문제를 찾는가?

아래 항목을 체크리스트로 쓰되 여기에 한정하지 않는다. 항목별 판단 기준이 더 필요하면 괄호 안의 문서를 읽는다.

- A. 현재 상태와 작업 현황: 선택한 대상, 작업 단계, 저장·처리·완료·실패 여부, 남은 작업, 마감 시각을 한눈에 알 수 있는가? 여러 화면을 오가거나 기억해야만 진행 상황을 알 수 있지는 않은가?
- B. 로딩·대기·진행: 최초 로딩, 부분 로딩, 업로드, 생성, 저장, 새로고침에서 무슨 작업이 진행 중인지 알 수 있는가? 설명 없는 스피너, 멈춘 것처럼 보이는 화면, 일부만 끝났는데 전체 완료처럼 보이는 표시가 있는가?
- C. Layout shift와 시각적 안정성: 이미지, 폰트, 데이터, 배너, 검증 메시지, 스켈레톤 전환 때문에 본문이나 버튼이 갑자기 움직이는가? 누르려던 대상이 이동하거나 스크롤이 튀거나 모달·토스트가 주요 정보를 가리는가? 관찰된 이동과 실제 불편을 기록한다. ([전이 중 유지 조건](transition-stability.md))
- D. 행동의 명확성과 클릭 가능성: 주요·보조 버튼이 구분되는가? 클릭할 수 있는 요소가 그렇게 보이고, 클릭할 수 있어 보이는데 반응하지 않는 요소는 없는가? 버튼 문구로 결과를 예측할 수 있고, 비활성화 이유와 활성화 조건을 알 수 있는가? ([사용성 리뷰](usability-review.md))
- E. 성공·실패·빈 상태의 구분: 데이터 없음, 검색 결과 없음, 로딩 중, 권한 없음, 오류가 서로 구분되고 각각 다음 행동을 안내하는가? 오류가 빈 화면이나 성공 화면처럼 보이지 않는가? ([상태별 안내와 다음 행동](state-design.md))
- F. 입력과 검증: 형식, 필수 여부, 제한 조건이 행동 전에 안내되는가? 오류가 해당 필드 가까이에 구체적인 수정 방법과 함께 나오는가? 실패 뒤 입력값이 남고 같은 정보를 다시 입력하게 하지 않는가?
- G. 저장·확정·취소·복구: 임시 저장, 저장, 확정, 예약, 완료의 의미가 구분되고 되돌릴 수 있는 행동인지 알 수 있는가? 저장하지 않은 변경이 조용히 사라지거나, 취소했는데 적용되거나, 저장했는데 다시 사라지지 않는가?
- H. 탐색과 문맥 유지: 뒤로 가기나 상세 화면 복귀 때 검색어, 필터, 페이지, 스크롤 위치, 선택 대상이 적절히 남는가? 현재 위치와 돌아가는 방법을 쉽게 알 수 있고, 같은 결과에 불필요하게 많은 단계를 거치지 않는가?
- I. 정보 구조·문구·일관성: 중요한 정보가 덜 중요한 정보에 묻히지 않는가? 상태명, 버튼명, 날짜·시간 형식, 오류 표현이 일관적인가? 내부 용어나 애매한 표현 때문에 뜻을 추측해야 하지 않는가? 마감이나 예약처럼 시간에 민감한 기능은 기준 시각을 이해할 수 있는가?
- J. 반응형과 기본 접근성: 작은 화면에서 잘림, 겹침, 가로 스크롤, 화면 밖 버튼이나 모달이 있는가? 색만으로 상태를 구분하거나, 클릭 영역이 작거나, 대비가 낮거나, 포커스가 보이지 않는가? 마우스 탐색을 기본으로 하되 주요 입력과 모달에서는 Tab, Enter, Escape 같은 기본 키보드 동작도 확인한다.
- K. 사용자에게 보이는 성능: 클릭 뒤 반응 지연, 반복 로딩, 입력 지연, 상태 반영 지연, 스크롤 끊김이 실제 작업에 어떤 영향을 주는가? 요청 수가 많거나 반복된다는 사실만으로 UX 문제나 중복 처리라고 단정하지 않고, 보이는 현상과 기술적 원인 추정을 나눈다.

## 2. 방법 결정: 어떤 증거를 어떤 방법으로 얻을 것인가?

### 탐색 원칙: 화면을 보고 실제 UI를 조작하는가?

실제 브라우저에서 화면을 관찰하고, 마우스로 클릭하고, 입력창에 입력하고, 스크롤하는 방식이 기본이다. 일반 사용자가 화면에서 발견할 수 있는 경로로 작업하고, URL 직접 입력, API 직접 호출, DB 수정으로 사용자 흐름을 건너뛰지 않는다. 이미 발견한 화면의 재방문이나 딥링크 동작을 검증하는 경우는 예외다.

DOM이나 접근성 트리는 요소를 찾거나 관찰을 돕는 데 쓸 수 있지만, 텍스트나 DOM만 읽고 시각적 UX를 확인했다고 판단하지 않는다. 레이아웃, 가독성, 겹침, 잘림, 피드백, 상태 변화는 실제 렌더링된 화면으로 확인한다. 개발 지식이나 내부 구현을 알아야 이해되는 화면을 설명할 수 있다는 이유로 괜찮다고 평가하지 않고, 사용자가 그 정보를 화면에서 알 수 있는지로 평가한다.

버튼을 눌렀다는 사실만으로 여정이 성공했다고 판단하지 않는다. 기대한 결과가 화면에 나타나는지, 필요하면 새로고침하거나 다시 방문해도 결과가 유지되는지까지 확인한다.

### 탐색 절차: 세 번에 나눠 무엇을 보는가?

#### 1차: 처음 쓰는 사람처럼 전체 흐름 보기

각 화면에서 행동하기 전에 화면의 목적과 현재 위치가 분명한지, 가장 중요한 정보와 다음 행동이 눈에 들어오는지, 지금 할 일과 이미 끝난 일을 구분할 수 있는지, 버튼을 누르면 무슨 일이 일어날지 예측할 수 있는지 본다. 화면을 해석하려고 여러 메뉴를 돌아다니거나 기억에 의존하거나 추측해야 했던 지점을 기록한다.

#### 2차: 주요 여정을 끝까지 수행

각 행동을 행동 전, 클릭 직후, 처리 중, 성공·실패, 이후 재방문 구간으로 나눠 관찰한다. 빠르게 연속 클릭해 최종 화면만 보지 않고, 클릭 직후 피드백과 대기 중 변화와 완료 시점의 표시를 확인한다. 도구가 지원하면 영상이나 브라우저 trace로 짧은 전환 상태를 보완한다.

특히 행동이 접수되었다는 표시가 바로 나타나는지, 처리 중에 다시 클릭하거나 다른 화면으로 이동할 수 있는지, 완료 전인데 완료된 것처럼 보이지 않는지, 완료 뒤 다음 행동과 결과 확인 위치가 분명한지, 목록·상세·배지·카운트에 같은 상태가 표시되는지 확인한다.

#### 3차: 실수·중단·복귀 상황

허용된 테스트 범위 안에서 빈 입력·잘못된 형식·긴 입력·경계값, 취소·뒤로 가기·모달 닫기·같은 화면 재진입, 저장 전 이탈·새로고침·저장 뒤 재방문, 연속 클릭·중복 제출·처리 중 다른 행동, 검색 결과 없음·필터 조합·필터 초기화, 긴 목록·긴 제목·이미지 로딩 실패 같은 데이터 변화, 오류 뒤 수정·재시도·복구를 확인한다. 느린 네트워크, 일시적 오프라인, 세션 만료, 일부 요청 실패는 도구와 환경이 지원하고 안전하게 재현할 수 있을 때 더한다. 일부러 만든 장애와 기본 환경에서 자연히 생긴 문제를 구분한다.

### HAR와 화면 증거: 네트워크 기록과 화면이 서로 이어지는가?

HAR만으로 UX 문제를 설명하지 않고 네트워크 기록과 화면 관찰을 연결한다.

HAR는 로그인 전부터 기록해 주요 여정을 빠짐없이 담는다. 파일이 커지면 여정 단위로 나누되 빠진 구간이 있는지 적는다. 여정 ID, 시작·종료 시각, HAR 파일명을 연결하고, 문제와 관련된 요청의 시각, 메서드, 경로, 상태 코드, 소요 시간을 가능한 범위에서 적는다. 탐색이 끝나면 HAR를 정상적으로 내보내고 파일이 있으며 예상한 요청 구간이 담겼는지 확인한다.

화면 증거는 주요 화면과 중요한 상태 전환을 캡처하고, layout shift·로딩·상태 불일치는 가능하면 전후를 남긴다. 스크린샷 파일명에 여정 ID나 문제 ID를 넣고, 영상이나 trace가 있으면 해당 시점도 연결한다. 정지 이미지 한 장으로 입증할 수 없는 현상을 그 이미지가 완전히 증명한다고 쓰지 않는다.

민감정보는 HAR의 헤더뿐 아니라 URL, 요청 본문, 응답 본문에도 들어 있을 수 있으므로 모두 점검한다. 공유용 HAR와 보고서에서는 가리고, 원본이 필요하면 공유용 산출물과 분리해 제한적으로 다룬다. 스크린샷과 trace에도 같은 원칙을 적용한다.

HAR, 영상, 특정 네트워크 조건을 도구가 지원하지 않으면 무엇을 수집하지 못했는지 밝히고 가능한 증거로 보완한다. 네트워크 요약을 HAR 파일이라고 부르지 않는다.

### 테스트 데이터: 어떤 데이터로 무엇까지 해도 되는가?

가능하면 직접 만든 식별 가능한 QA 데이터를 쓰고, 삭제·취소·초기화는 원칙적으로 직접 만든 QA 데이터에만 한다. 현재 QA 계정의 접근 범위 안에서 탐색한다. 끝나면 생성한 데이터와 남은 예약·작업을 확인하고, 정리한 항목과 남겨 둔 항목을 기록한다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 발견 사항 형식: 다른 사람이 보고 재현할 수 있는가?

```markdown
#### UX-001. [사용자가 겪는 문제를 구체적으로 표현한 제목]
- 분류: 기능 오류 / 사용성 문제 / 시각적 문제 / 접근성 문제 등
- 심각도: 중대 피해 / 차단 / 큰 마찰 / 작은 마찰
- 여정 및 위치: 여정 ID, 화면, URL 경로, 관련 요소
- 발생 조건: 데이터 상태, 화면 크기, 네트워크 조건 등
- 재현 절차: 실제 수행한 행동을 번호 순서대로
- 관찰한 실제 결과: 화면에서 무엇이 어떻게 나타났는지
- 기대되는 사용자 경험: 사용자가 무엇을 알거나 할 수 있어야 하는지
- 사용자 영향: 헷갈림, 재확인, 작업 지연, 오조작, 데이터 손실 등
- 재현 여부: 재현됨 / 간헐적 / 1회 관찰 / 추가 검증 필요
- 증거: 스크린샷·영상·trace·HAR 파일과 해당 시각 또는 요청
- 원인 추정: 필요할 때만, 관찰 사실과 구분해서
- 개선 제안: 그 불편을 줄이는 구체적인 방향
- 개선 확인 기준: 수정 뒤 어떤 행동과 화면을 보면 해결로 판단할지
```

### 최종 보고서: 담당자가 이것만 보고 고칠 수 있는가?

보고서는 다음 순서로 쓴다.

1. 핵심 요약: 주요 장애물과 가장 먼저 고칠 문제를 정리하고, 기능 실패와 동작은 하지만 쓰기 어려운 문제를 구분한다.
2. 탐색 범위와 커버리지: 발견한 화면과 여정 목록을 주고, 여정마다 정상 완료, 로딩·처리 중, 빈 상태, 입력 검증·오류·재시도, 취소·뒤로 가기·이탈, 새로고침·재진입, 좁은 화면이나 모바일, 관련 증거를 공통 판정으로 표에 정리한다.
3. 문제 목록과 상세: 심각도와 영향받는 여정 기준의 요약 표 뒤에 각 문제를 위 형식으로 쓴다.
4. 반복되는 UX 패턴: 상태 표시 부재, 저장 의미 혼동, 문맥 손실, 불안정한 레이아웃처럼 여러 여정에 공통인 문제를 묶는다.
5. 확인하지 못한 항목과 한계: 접근 권한, 테스트 데이터, 외부 실행 제한, 도구 제약, 재현 실패로 남은 부분을 구체적으로 쓴다.
6. 증거와 테스트 데이터 정리: 실제 생성한 HAR·스크린샷·영상·trace의 경로나 링크, 여정별 대응, 생성·정리한 QA 데이터와 남은 작업을 정리한다.

발견한 핵심 여정은 종료 상태까지 수행하고 주요 분기와 UX 상태를 확인한 뒤 마무리한다. 시간이나 도구 한계가 생기면 핵심 여정과 영향이 큰 문제를 먼저 다루고 나머지는 미검증으로 남기며, 확인하지 않은 범위까지 묶어 모든 여정에 문제가 없다고 결론 내리지 않는다. 목표는 담당자가 이 보고서만으로 사용자가 어디에서 무엇 때문에 불편을 겪는지, 어떻게 재현하는지, 무엇을 바꾸면 해결되는지 이해하게 하는 것이다.
