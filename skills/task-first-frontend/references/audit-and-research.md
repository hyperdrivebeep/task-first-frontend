# 실제 화면 관찰과 과업별 레퍼런스

S2(비포 캡처)와 S3(레퍼런스) 단계 문서다. 산출물은 `01-before/`, `02-refs/INDEX.md`, `02-refs/ref-*.png`이고 형식은 [work-folder.md](work-folder.md)에 있다. 게이트: `--stage 2`, `--stage 3`.

## 현재 화면 관찰

적용 브라우저 스킬/도구 문서를 먼저 읽고 지원 API만 사용한다. 기존 탭이 정확한 대상이면 상태를 먼저 읽는다. 새로고침이나 이동으로 사용자 입력을 잃지 않는다. 조사 탭은 기본적으로 백그라운드에 두고 사용자가 볼 결과만 열어 둔다.

1. 최신 DOM/접근성 상태에서 이동할 제어를 찾는다.
2. 과업에 필요한 행동만 수행한다. 읽기 감사에서 모델 생성·권한 변경·저장·승인·복원을 실행하지 않는다.
3. 가장 가벼운 관찰로 변경을 확인한다. 구조는 DOM, 배치/가독성은 스크린샷으로 본다.
4. 로딩·빈 화면·오류·잘못된 탭을 구분한다. 이유 없는 고정 sleep을 반복하지 않는다.
5. 캡처한 그 이미지를 로컬에 저장하고 직접 연다. 잘못된 캡처는 제외하고 재촬영한다.
6. 단계/과업/화면 상태/장점/문제/사용자 영향/개선 가설/한계/파일을 기록한다.

게이트가 읽는 비포 파일은 `01-before/before-<screen>-<width>.png`다. 흐름 단계별 캡처를 더 남기려면 `before-<screen>-<width>-<state>.png`처럼 상태를 붙인다. 캡처와 설명을 함께 남기고 각각이 지지하는 주장을 적는다.

핸들이 사라졌으면 탭 목록 확인 후 대상 핸들을 다시 얻는다. 변경된 DOM에 옛 인덱스를 재사용하지 않는다. 임의의 다른 브라우저나 비공식 자동화 경로로 전환하지 않는다.

뷰포트는 실제 환경을 기록한다. 더 예쁘게 보이게 하려고 넓히지 않는다. 반응형 시험에 필요한 크기만 명시적으로 설정하고 임시 설정은 복원한다. 에뮬레이션을 실기기 확인이라고 쓰지 않는다.

## 관찰할 문제

- 진입/복귀: 최신 내용과 옛 실패를 구분하는가, 이어갈 위치와 맥락을 찾는가.
- 정보 우선순위: 설정/기술 설명이 과업을 아래로 밀어내는가, 긴 제목이 반복되는가.
- 비교: 같은 비교축을 동시에 볼 수 있는가, 앞 문장을 기억하며 내려가야 하는가.
- 근거: 전체 목록과 특정 인용의 직접 이동은 다른 경로다. 일반 버튼만 보고 직접 이동이 없다고 단정하지 않는다.
- 행동: 제출/이동, 요청 준비/실행, 취소 요청/종료 확인이 구분되는가.
- 상태: 로딩/실패/부분/보류/미대조/stale을 오인하지 않는가.
- 접근성: 한글 긴 문장, 작은 보조 글씨, 중첩 스크롤, 키보드 초점, 터치, 확대의 위험이 있는가.

한 세션의 관찰을 제품 전체의 동작으로 일반화하지 않는다. 스크린샷만으로 대비비·WCAG 준수·키보드 동작을 인증하지 않는다.

## 레퍼런스 조사

과업을 정한 뒤 검색한다. '예쁜 AI dashboard' 대신 '인용 원문을 확인하고 돌아오는 방식', '행을 선택해 비교 맥락을 유지하는 상세 보기'처럼 검색한다.

### 어디서 찾나 (사용자 가이드, 먼저 본다)

작성자가 정리한 두 가이드가 이 단계의 기준이다. 레퍼런스 조사 전에 **스킬 안 사본**을 열어 읽는다(원본은 작성자 Drive 문서라 접근 권한이 필요할 수 있어 에이전트가 못 열 수 있다).

사본은 2026-11-23에 원본에서 옮겨 왔다. 원본이 바뀌었을 수 있으니 원본을 열 수 있으면 두 버전의 날짜를 비교한다.

핵심: 사이트가 아니라 **지금 결정에 필요한 증거 유형(artifact)** 을 먼저 정하고 그에 맞는 곳에서 찾는다.

| 알고 싶은 것 | 필요한 artifact | 시작점 | 쓰면 안 되는 용도 |
| --- | --- | --- | --- |
| 실제 제품의 화면·상태 | screenshot, captured flow | [Mobbin](https://mobbin.com/), [Refero](https://refero.design/), [Pttrns](https://www.pttrns.com/), [Nicelydone](https://nicelydone.club/) | 사용성·전환 효과 증명 |
| 과업이 어떤 순서로 진행되는가 | 녹화된 완전한 흐름 | [Page Flows](https://pageflows.com/), Mobbin flow/video | 모든 분기·오류 상태가 있다고 가정 |
| 왜 그렇게 설계했나·원칙 | 연구·가이드라인 | [NN/g](https://www.nngroup.com/), [Baymard](https://baymard.com/), 공식 디자인 시스템(GOV.UK, USWDS 등) | 대상 제품에서의 효과로 단정 |
| 어떻게 구현하나 | 명세·코드 | 대상 제품이 이미 쓰는 컴포넌트 라이브러리의 공식 문서 | 라이브러리 교체를 UX 개선으로 간주 |
| 랜딩·페이지 구성 | 페이지 갤러리 | [One Page Love](https://onepagelove.com/), [Land-book](https://land-book.com/) | 앱 과업 흐름 근거 |

- 대부분 화면 모음 사이트는 로그인·유료다. **로그인이 필요하다는 이유로 건너뛰지 않는다.** 조사를 시작하기 전에 사용자에게 "로그인된 사용자 브라우저로 봐도 되는가"를 묻고, 허락되면 사용자 브라우저(에이전트가 붙는 방식, 새 프로필·헤드리스 아님)로 연다. 쿠키·캐시·기록을 지우지 않고, 계정 설정·결제·저장·구독 같은 계정 행동은 하지 않는다.
- 허락이 없거나 열리지 않으면 **그 자리에서 대화창으로 알린다.** 어느 사이트를 못 봤는지, 대신 무엇을 봤는지, 그래서 어떤 결론이 약해지는지. 설계 문서에만 "보지 못함"으로 적고 넘어가지 않는다.
- **방문 범위:** 위 표와 가이드 표에 있는 사이트 중 지금 과업과 관련된 곳은 **모두** 방문한다. 빼도 되는 이유는 허용 목록뿐이고 사이트마다 적는다: 유료·구독, 로그인·계정 필요(사용자 브라우저 사용이 허락되지 않았거나 열리지 않을 때), 차단·403·캡차·지역 제한, 과업과 무관(그 과업 ID를 함께). 형식은 [work-folder.md](work-folder.md)의 방문표다. 대상 목록은 [site-list.json](site-list.json)이고 계약의 `ref_tags`로 고른다. 결과는 `02-refs/INDEX.md` 방문표에 적고, `visited`로 적은 사이트는 캡처가 차용표에 있어야 한다. "못 봄"만 적으면 게이트가 FAIL을 낸다.
- **최소 조사량:** 과업 하나마다 비교 가능한 화면·흐름 3~5개를 서로 다른 출처 2곳 이상에서 모은다. 그중 1곳 이상은 실제 출시 화면 모음(Mobbin·Refero·Page Flows 등)이고, 나머지는 원칙(NN/g·공식 디자인 시스템)이나 제품 직접 사용이어도 된다. 부족하면 시안 단계로 넘어가지 않는다.
- **레퍼런스 캡처 저장:** 본 화면을 그대로 캡처해 작업 공간에 둔다. 파일명 `02-refs/ref-<사이트>-<제품>-<화면·상태>.png`, 차용표 한 행씩, 기록에는 URL·캡처일·플랫폼·제품명·출시 화면/컨셉 구분. 이 캡처가 뒤의 출처 보고(design-and-ideation.md)의 재료다. 유료 사이트 캡처는 내부 검토용으로만 두고, 공개 저장소에는 사이트 약관을 확인한 뒤 올린다(모르면 비공개 저장소나 링크로 대신).
- 같은 사이트 안에도 실제 출시 화면·AI 생성 컨셉·광고가 섞인다. 사이트가 아니라 개별 화면(캡처 날짜·플랫폼)과 그것이 지지하는 주장 단위로 기록한다.
- 결정에 필요한 동종 흐름을 비교해 공통 규칙과 변형점을 뽑는다. 위 최소 조사량(과업마다 3~5개, 출처 2곳 이상)은 하한이다. 그 위로는 사이트·자료 수를 고정하지 않고 근거의 관련성과 충분성으로 판단하며, 하한을 채우려고 관련 없는 화면을 넣지 않는다.

- 공식 문서, 디자인 시스템, 직접 접근 가능한 화면을 우선한다.
- 검색 요약은 후보 탐색에 쓰고 중요한 주장은 본문을 연 뒤 판단한다.
- 조사일과 버전을 기록한다. 과거 링크를 현재 동작으로 단정하지 않는다.
- 제품을 나열하는 대신 적용할 원리를 추출한다. 충분한 근거를 확보하면 검색을 멈춘다.
- 계정이 필요한 흐름을 공식 문서만 읽고 직접 테스트했다고 하지 않는다.
- 지정된 핵심 레퍼런스에 접근할 수 없으면 영향과 대안을 알린다. 조용히 무시하거나 읽었다고 하지 않는다.

레퍼런스 기록은 [설계 문서 양식](../assets/design-brief-template.md#레퍼런스-적용)에 남긴다.

- 사이트명과 **개별 artifact URL/위치**, 관찰일, 자료의 캡처일·플랫폼(알 수 없으면 미상), 보존한 캡처/발췌 경로를 적는다. 캡처가 없으면 없다고 쓴다. 홈페이지 URL만으로 개별 흐름을 관찰한 증거를 대신하지 않는다.
- 실제 확인 수준(직접 조작 / 녹화 / 정적 이미지 / 문서 / 홈페이지·검색 요약만 / 접근 불가)과 본 화면·단계 범위를 적는다. **관찰 사실**과 그로부터 **추론한 원리**를 분리한다.
- 채택·부분 채택·미채택과 이유, 반대 증거·부작용·트레이드오프를 남긴다. 검토한 후보 중 불리하거나 적용하지 않은 근거를 성공 사례만 남기려고 지우지 않는다.

이미지가 있으면 직접 보고, 생성에 쓸 때 실제 파일/참조를 첨부한다. 문서 사이트의 사이드바나 색을 대상 제품 테마로 오인하지 않도록 역할을 명시한다.

외부 자료는 그 제품의 동작을 설명한다. 현재 제품에도 더 효과적이라는 판단은 별도 가설이다. 인용으로 이 구분을 숨기지 않는다.

## 설계로 연결

주요 변경마다 안정적인 `changeID`(예: `C-01`)를 부여해 `사용자 문제 → 화면/코드 근거 → 개별 참고 자료·원리 → 제안 구조 → 보존할 계약 → 비교 시험`을 연결한다. 같은 ID를 구현·검증·최종 보고까지 유지하고 관련 레퍼런스 행마다 붙인다. 사용자에게 보이는 영향도 확인할 과업도 없는 변경은 핵심에서 제외한다.

변경 전에 과업 가설·기록일·기대 결과·비교 조건/판정 기준과 기존 증거를 남긴다. 구현 후 정리했다면 **사후 해석**과 실제 기록일을 표시하고 사전 가설처럼 쓰지 않는다. 아직 채택하지 않은 후보는 관련 ID 또는 미연결 사유를 기록한다.

실제 화면에 접근하지 못해도 코드/레퍼런스 조사는 가능하다. 이때 정적 분석 기반 설계로 보고하고 '현행 UI 감사 완료'라고 하지 않는다. 화면 접근 실패를 가짜 캡처로 보완하지 않는다.
