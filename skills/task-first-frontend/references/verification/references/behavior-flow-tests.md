# 행동 흐름 테스트 설계

이 문서는 여러 행동과 상태 변화가 이어지는 기능에서 개별 동작이 이어지거나 중단·재시도될 때도 기대한 결과와 일관성이 유지되는지 검증하는 테스트를 설계하고 실행할 때 쓴다. 테스트 범위는 요청받은 기능과 직접 영향을 받는 흐름으로 한정한다.

## 1. 필요성 판단: 무엇을 이해하거나 검증해야 하는가?

### 기대 동작과 범위: 무엇을 증명하려는가?

요구사항, 기존 결정, 구현, 테스트에서 사용자가 달성하려는 결과, 주요 행동과 그 행동으로 달라지는 상태, 상태를 소유하는 주체와 유지 기간, 외부 시스템·비동기 처리·영속화가 끼어드는 경계, 실패·중단·재시도 때 기대하는 동작을 파악한다.

### 연속 시나리오 확장: 어느 경계에서 깨지기 쉬운가?

먼저 대표 정상 흐름을 정하고, 그 흐름에서 오류가 나기 쉬운 경계를 찾아 관련 변형을 고른다.

순서 관점에서는 이전 작업이 늦게 완료되거나 처리 순서가 뒤바뀌는 경우를 본다. 반복 관점에서는 중복 실행, 재시도, 같은 대상 재방문을, 중단 관점에서는 취소, 이탈, 종료, 연결 끊김을 본다. 복구 관점에서는 재접속, 재시작, 저장 상태로의 복원을 보고, 동시성 관점에서는 여러 작업·사용자·클라이언트가 같은 상태를 바꾸는 경우를 본다. 대상 변경은 작업 도중 계정·항목·조건·컨텍스트가 바뀌는 경우이고, 부분 실패는 일부 단계만 성공하거나 성공 응답이 유실되거나 후속 처리가 실패하는 경우다. 경계 데이터로는 비어 있음, 한도 도달, 삭제됨, 권한 변경을 본다.

변형은 해당 기능과 관련 있을 때만 적용하고, 데이터 유실, 잘못된 대상 처리, 중복 부작용, 복구 불가 위험을 먼저 다룬다.

### 판정 기준 선기록: 실행 전에 무엇을 정해 두는가?

테스트 코드를 쓰거나 도구를 조작하기 전에 초기 조건, 행동과 외부 사건의 순서, 지연·실패·동시 실행 같은 조건의 재현 방법, 처리 중 관찰되어야 할 동작, 최종 결과와 허용되지 않는 부작용, 실행 결과를 판정할 증거를 정한다.

관련된 불변 조건도 적는다. 예를 들면 다음과 같다.

- 결과는 해당 요청·대상·버전에만 적용된다.
- 오래된 결과가 최신 상태를 덮어쓰지 않는다.
- 재시도해도 허용되지 않은 중복 부작용이 생기지 않는다.
- 미확인·실패·빈 결과를 서로 혼동하지 않는다.
- 사용자 입력과 이미 확정된 데이터가 정해진 규칙에 따라 보존된다.
- 완료 보고와 실제 저장·처리 결과가 일치한다.
- 중단된 작업을 다시 시작하거나 복구할 수 있다.

## 2. 방법 결정: 어떤 증거를 어떤 방법으로 얻을 것인가?

### 테스트 층 선택: 이 결함을 잡을 수 있는 층은 어디인가?

로직 테스트는 전환 규칙, 계산, 검증, 충돌 해결을 맡고, 통합 테스트는 구성 요소 사이의 호출, 영속화, 외부 시스템 계약을 맡는다. 상호작용·종단 간 테스트는 실제 진입점에서 시작하는 연속 작업을 맡는다. 빠르고 안정적인 하위 층에서 세부 조건을 검증하고, 주요 흐름은 실제 구성 요소가 연결된 상태에서 확인한다. 정적 출력 검사로 실행 중 변화를 검증했다고 주장하지 않는다. 기존 테스트를 되풀이하기보다 빠진 경계와 연결을 채운다. 도구 선택과 실행은 프로젝트의 기존 지침을 따른다.

### 조건 통제와 관찰: 과정까지 보고 있는가?

가능하면 시간, 응답 순서, 실패 지점을 명시적으로 통제한다. 오래된 결과의 영향을 검증하는 예는 다음 순서다.

1. 작업 A를 시작하고 완료를 보류한다.
2. 조건을 바꿔 작업 B를 시작한다.
3. B를 완료하고 결과를 확인한다.
4. A를 뒤늦게 완료한다.
5. 정해진 최신성 규칙과 부작용 조건이 유지되는지 확인한다.

대상 전환에 적용하면 이렇다. 사용자가 다른 대상(계정·프로젝트 등)으로 전환했다면 이전 대상에 대한 늦은 응답을 현재 대상의 데이터로 표시하지 않는다. 전환과 함께 선택을 초기화해야 한다면 새 대상 화면의 전이 조건에 그 동작을 명시한다. 동시 요청을 시험할 때는 두 요청의 시작을 각각 확인한 뒤 응답을 의도한 순서로 완료하고, 현재 조회 대상에 맞는 데이터만 화면에 반영되었는지 검사한다. 마지막 응답이 화면에 표시되었는지만 보면 오래된 응답의 덮어쓰기를 놓친다.

최종 결과만으로 놓칠 수 있는 문제는 처리 중에도 관찰하고, 필요하면 출력, 이벤트, 요청, 저장 결과를 이어서 확인한다. 관련 오류가 없는지도 확인한다. 재현에 필요한 조건을 만들지 못하면 미검증으로 남긴다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 회귀 테스트와 탐지력: 이 테스트는 결함이 있을 때 실패하는가?

수정 작업이 범위에 들어 있으면 원인을 드러내는 최소 재현 테스트를 만들고, 가능하면 수정 전 실패와 수정 후 통과를 확인한 뒤 영향을 받는 연결 흐름을 검증한다. 우연한 성공이나 단순 재실행으로 실패를 덮지 않는다.

새 검사 체계를 만들거나 반복 누락을 보강할 때는 관련된 작은 결함을 격리된 테스트 환경에 일부러 넣어 검사가 실패하는지 확인한다. 매번 전체 E2E 실행에 강제하지는 않는다. 넣어 볼 결함의 예는 수량 불일치, 보이지 않는 버튼, 화면 밖 팝오버, 처리 중 중복 요청, 성공 후 남는 오류 안내, 늦은 응답에 의한 선택 덮어쓰기, 재조회 중 툴바 이동이다. 각 결함은 그것을 잡아야 할 검사에서 올바른 이유로 실패해야 하며, 무관한 서버 오류나 시간 초과는 탐지 성공으로 치지 않는다. 결함을 되돌린 뒤 정상 실행도 확인하고, 정상 실행·결함 실행·복구 실행의 결과를 나눠 적는다.

### 보고: 시나리오별로 무엇이 남았는가?

시나리오마다 공통 판정을 붙이고, 검증 대상과 환경·버전, 실행한 주요 시나리오와 결과, 재현 테스트나 실행 증거의 위치, 모킹·관찰 범위와 중요한 미검증 항목, 발견한 문제와 남은 결정을 적는다.
