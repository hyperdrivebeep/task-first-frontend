# 실제 사용자 테스트

이 문서는 두 표현 중 어느 쪽이 이해하기 쉬운지, 첫 행동을 찾을 수 있는지, 팀의 디자인 논쟁 중 무엇이 실제로 통하는지처럼 화면 관찰만으로 결정하기 어려운 문제를 실제 사용자로 확인할 때 쓴다. 에이전트의 화면 검토와 브라우저 검증은 실제 사용자 조사에 해당하지 않으므로 실제 사용자 테스트라고 부르지 않는다.

## 1. 필요성 판단: 무엇을 이해하거나 검증해야 하는가?

### 테스트가 필요한지: 관찰로 풀 수 없는 질문인가?

포커스 그룹은 욕구·의견·가치 제안을 탐색할 수 있지만, 한 사람씩 과업 수행을 관찰하는 사용성 테스트를 대신하지 않는다. 큰 막판 연구를 기다리기보다 이른 단계부터 작은 반복 테스트를 계획한다. 책의 저비용 반복 방식은 한 라운드에 3~4명을 권하지만 제품의 위험도와 연구 목적에 맞게 조정하며, 통계적 증명을 위한 표본 수로 쓰지 않는다. 완벽한 대표 참가자를 구하느라 늦추지 말고 대상 사용자와의 차이를 적은 뒤 결과를 그 조건에 맞게 해석한다.

휴리스틱 리뷰만 요청받았다면 참가자 모집, 연락, 녹화, 테스트 예약을 시작하지 않고 보고서에 테스트 제안으로 남긴다. 테스트 진행 자체를 요청받았을 때 [저자의 테스트 자료 모음](https://sensible.com/download-files/)에서 최신 진행 스크립트와 관찰자 자료를 열어 필요한 절차를 확인하며, 그 파일을 스킬에 복사해 배포하지 않는다.

## 2. 방법 결정: 어떤 증거를 어떤 방법으로 얻을 것인가?

### 진행: 답을 알려 주지 않고 어떻게 관찰하는가?

1. 대상 사용자와 의미 있는 과업을 정한다. 경쟁 제품, 스케치, 와이어프레임, 프로토타입, 실제 화면 어느 단계에서도 시작할 수 있다. UI 라벨이나 클릭 경로를 정답처럼 알려 주지 않는다. "다음 주 예약을 다른 날로 바꾸고 변경됐는지 확인해 주세요"처럼 쓰고, "설정 탭을 누르세요"처럼 정답 경로를 과업 문구에 넣지 않는다.
2. 처음 보는 화면에서 무엇을 할 수 있을 것 같은지 설명하게 한다. 진행을 유도하는 힌트 없이 첫 선택과 예상 결과를 관찰한다.
3. 과업을 수행하며 생각을 말하게 한다. 진행자는 중립적으로 듣고 경로를 가르치지 않으며, 멈췄을 때만 "지금 무엇을 생각하고 있나요?"처럼 유도하지 않는 질문을 쓴다. 보조기술과 이용 환경을 고려한다.
4. 어느 문구에서 멈췄는지, 무엇을 잘못 예상했는지, 첫 번째로 그럴듯한 경로가 무엇이었는지, 도움이나 되돌아가기가 필요했는지 기록한다. 관찰자도 각자 가장 심각한 문제를 몇 개만 적는다.
5. 관찰된 행동, 참가자 의견, 팀의 해석을 구별한다. 참가자 표현은 실제 기록이 있을 때만 인용한다. 새 기능 요청을 바로 요구사항으로 만들지 말고 그 요청 뒤에 막힌 과업을 확인한다.

## 3. 검증 및 활용: 무엇을 확인했고 어떤 판단에 반영할 것인가?

### 정리와 재테스트: 무엇부터 고치고 어떻게 다시 보는가?

세션 직후 관찰자와 가장 심각한 문제부터 합의한다. 쉬운 잔수정이 큰 문제를 밀어내지 않게 하고, 설명을 더하기보다 불필요한 요소를 빼거나 선택을 분명히 하는 해결책을 먼저 검토한다. 사용자가 문제를 바로 알아차리고 도움 없이 빠르게 회복하며 불쾌감이나 후속 위험이 없다면 우선순위를 낮출 수 있다. 그렇지 않으면 결국 성공했다는 이유로 문제를 무시하지 않는다.

수정했다면 가능할 때 같은 과업과 조건으로 다시 테스트한다. 재모집이나 실행이 불가능하면 재검증 계획과 미확인 범위를 남긴다. 적은 수의 정성적 관찰을 전체 사용자의 성공률이나 선호도로 일반화하지 않는다.
